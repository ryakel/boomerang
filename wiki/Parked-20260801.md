## 1. Pin to today — give `committed_on` a writer in the web app

**Ready to build.** The only one of the four with no unknowns.

**What exists.** The entire server half, merged and tested:

- `POST /api/tasks/:id/commit` (`server/server.js:888`) — enforces the three-task ceiling, returns `409` with the current three when it's hit, accepts `force=true` (logged), stamps `committed_on` + `last_touched`, bumps the version and broadcasts.
- `POST /api/tasks/:id/uncommit` (`server/server.js:917`) — clears `committed_on`. Deliberately does **not** increment `boomerang_count`: changing your mind is not slipping.
- `POST /api/tasks/:id/complete` (`server/server.js:930`) — keeps `committed_on` so `GET /api/today` still shows the task in today's three, checked off.
- Siri already reaches it: `CommitToBoomerangTaskIntent` (`ios/App/App/BoomerangIntents.swift:262`).
- `GET /api/tasks?committed_today=true` (`server/server.js:795`) already filters on it.

**What's missing.** Exactly one thing: **`src/` never calls any of it.** A grep for `/commit` across the client finds only `/api/adviser/commit` (`src/api.js:1954`), which is Quokka's staged-execution commit — unrelated. So the only surfaces that can write `committed_on` today are Siri and the watch.

**The decision.** Not plumbing — placement. The Kept row (`.bm-row`) is already a checkbox plus a full-width body button, so a third affordance needs a home: swipe action, long-press, or an action in the task detail sheet. Pick one before writing code.

**Why it matters more than it looks.** The v2.49.0 watch fallback exists *because* nothing is ever committed. The digest has run its fallback path permanently for the same reason (`server/digestBuilder.js`, `threeMode = 'today' | 'empty'`). One writer lights up the intended path in three surfaces at once — Today, the digest, and the wrist.

**Effort:** S (client only). **Risk:** low — additive, and the endpoints already have coverage.

## 2. Packages drive due dates

The originating report: *"I couldn't change the fan blade arms until a package with those arms showed up."* A task whose real start condition is a delivery, not a date.

**What exists.** More than expected:

- `packages` (`migrations/009_create_packages_table.sql`) already carries `eta`, `delivered_at`, `status`, and `status_detail`.
- `signature_task_id` on the same table is a **working precedent for linking a package to a task** — the pattern doesn't need inventing, just generalizing.
- Package polling, status transitions and notification dispatch are all live (`server/server.js`, `server/pushNotifications.js`).

**What's missing.**

1. A task↔package link. `signature_task_id` points package → task for one specific purpose; this needs the general relation, which means a migration.
2. Logic on the poll path: when a linked package flips to delivered, set the task's `due_date` (today, or the delivery day). Reuse the `due_date_original` / `due_shifted_at` / `due_shifted_reason` provenance columns from `migrations/049_due_date_provenance.sql` — they were built for the away-window repair but the shape is exactly right here, and a shifted date with no recorded reason is the thing that makes dates untrustworthy.
3. UI to create the link, most naturally from the package row.

**The decision.** What the task looks like *before* delivery. Options: undated and out of the pool; dated to the `eta` and re-dated on actual delivery; or a new blocked/waiting state. This is a task-model question, not a packages question, and it determines whether the task nags you about something you cannot yet do — which is the whole complaint.

**Effort:** M (migration + server + UI). **Risk:** medium — it writes `due_date`, so a wrong rule produces false urgency. Provenance columns make it auditable and reversible.

## 3. Arrival reminders / geofencing

*"I need to do this first thing when I get home."* Explicitly kept as a wanted feature when away-mode was split off from it — these are two independent features and this one is still wanted.

**What exists.** Migration 046 shipped `location_json` — `{lat, lng, radius_m 50-1000, label, trigger: arrive|leave}` — validated (`server/taskModel.js:170-193`), stored, and filterable via `?has_location=true` (`server/server.js:741`). `geocode_location` exists as a Quokka tool (`server/adviserToolsMisc.js:310`). All of it is currently dead: no UI, no iOS code, no delivery.

**What's missing.** The whole native half — CoreLocation region monitoring in the Capacitor shell, a background-location entitlement, syncing the nearest N located tasks into BoomerangKit via the App Group (iOS caps region monitoring at 20), and local notification delivery. Plus a location picker in the task editor.

**Deliver locally, not from the server.** A local notification touches none of the server send paths and so is unaffected by the dev muzzle (`notifsMuzzled`) — and it fires only when action is possible in the next five minutes, which is the bar the Great Alert Deletion set for any new ping.

**Effort:** M native + S web. **Risk:** low logically, high in ceremony — **requires a Mac build session and an Xcode rebuild**, unlike items 1 and 2.

## 4. Calendar-based away detection

The redirect that produced away mode: detect the travel window from the calendar rather than geolocation, because *"the issue right now is remembering to set it."*

**What exists.** The entire away-window mechanism, shipped today: `server/vacationWindow.js` (pure, 23 tests), `server/vacationRepair.js` (pure, forward-only and idempotent, 17 tests), the `vacation_window` `app_data` key with `getVacationWindow()` / `setVacationWindow()` (`server/db.js`), suppression inside `isNotifiable()` with the `ignoreAway` escape hatch, and `/api/vacation` + `/api/vacation/repair`. GCal events are already fetched (`server/server.js:2203-2237`).

**What's missing.** Only the inference: which events mean *travelling*.

**The decision, and the reason this is last.** There is no reliable signal. Multi-day all-day events, location fields, title keywords and declined-meeting density are all heuristics, and both failure modes are bad in a way the user cannot see:

- **False positive** — the app silently suppresses home-task notifications during a week you were home.
- **False negative** — the current state, which at least fails loudly by nagging.

It also writes the window that now gates *both* notification suppression and bulk date shifting. **Never let inference write the window directly.** Propose it and let a human confirm — a one-tap "Heading out Aug 4–11?" card is the whole feature and removes the entire failure class.

**Effort:** M. **Risk:** high if it auto-applies, low if it only proposes.
